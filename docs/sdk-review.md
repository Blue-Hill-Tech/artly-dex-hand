# D21 SDK and simulation review

Reviewed the September 2026 D21 engineering package on October 21, 2026 (Pacific). Driver behavior is unchanged. ROS2 descriptions and URDF robot display names use Artly D21; original source packages are retained privately. Reproducible offline checks and results are in [tools/check_offline.py](../tools/check_offline.py) and [provenance/offline-validation.json](../provenance/offline-validation.json).

## Inventory and version evidence

- Standalone Python SDK: five `.py` files, `README.md`, and `API.md`. No package metadata or formal version field. README requires Python 3.8+, `pyserial`, and `python-can>=4.6.1`. Source local modification dates range from August 25 through September 3, 2026; these are filesystem metadata, not a verified release date.
- Source SDK exposes RS485 Modbus RTU and CAN FD Modbus-framed transport through CANable SLCAN. The tactile 8-bit read function `0x05` is a supplier protocol extension, not the standard Modbus write-single-coil meaning.
- ROS2 source was expanded under `sdk/ros2/hand_control` after checking archive CRC and paths. Generated bytecode and the original archive are not distributed here. No video entries were found.
- ROS2 package `hand_control`: version `0.0.1` in `package.xml` and `setup.py`; README targets Ubuntu 24.04 with ROS2 Jazzy and has document version `2026-09-02`. This is supplier-stated support, not an independently qualified platform matrix.
- Standalone Python README uses Windows `COM3` examples; ROS2 README uses `/dev/ttyACM0`. These demonstrate intended serial-port naming, not full cross-platform qualification.
- Simulation: two URDF models, two MuJoCo XML models, 40 STL files (20 per hand), two example scripts and README. All four standalone models have 21 movable joints. URDFs additionally contain fixed joints: 32 links and 31 joints total. Both XMLs have 21 actuators. The SDK takes 16 independent angle commands; example coupling rules drive the five distal joints.
- ROS2 URDFs differ from the standalone URDFs and should remain separate. ROS2 mesh directories contain 20 left-hand and 26 right-hand meshes; several extra right-hand pitch/rotate meshes are not referenced by its URDF. All referenced files are present.
- `CANFDDevice.py` is byte-identical between standalone and ROS2 packages. RS485 and CANFD wrapper differences include relative imports for ROS2. ROS2 `D21ModbusCore.py` additionally has `read_temp()` (input registers 48..63, divided by 10). Preserve both variants.

## Setup and usable entry points

Use an isolated virtual environment and quote the requirement specifier (the vendor unquoted `python-can>=4.6.1` can be interpreted by a shell as redirection):

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install pyserial 'python-can>=4.6.1'
```

The standalone SDK is a set of modules, not an installable package. Run Python from its directory or put that directory on a command-scoped `PYTHONPATH`. A safe import check is:

```sh
python -B -c 'import D21ModbusCore, d21_rs485, CANFDDevice, d21_canfd'
```

This only imports modules. Instantiating `d21_rs485` opens the serial port immediately; `d21_canfd` requires explicit `connect()` to open its bus. Default RS485 implementation is 500000 baud, 8N1 and 0.1 s timeout. Its docstring incorrectly says 115200. CAN FD wrapper defaults are arbitration 1 Mbps, data 2 Mbps, SLCAN serial 10 Mbps; verify adapter firmware and bus configuration before any hardware test.

`example.py` is a hardware actuation example, not a harmless import: top-level code opens a port, sets maximum fan, sets finger speeds to 80%, and commands joint positions. No such example was run.

For ROS2 on the supplier-stated platform, place `hand_control` inside a ROS2 workspace `src` directory, source `/opt/ros/jazzy/setup.bash`, resolve its ROS dependencies, install the Python dependencies above into the interpreter used by ROS2, then use `colcon build --packages-select hand_control --symlink-install`. The vendor package declares `pyserial`, but does not declare `python-can` in either package.xml or setup.py even though the node imports CANFD unconditionally. Thus `python-can` is needed even for an RS485 or simulation node import.

After building and sourcing `install/setup.bash`, the intended non-hardware launch is:

```sh
ros2 launch hand_control hand_control.launch.py use_simulation:=true hand_type:=right
```

This ROS2 launch was not tested locally: ROS2 Jazzy, `rclpy`, and the ROS2 runtime dependencies are absent. The host has ROS1 installations and a `colcon` executable, which does not establish ROS2 readiness.

The ROS2 node supports topics for 16 joint angles, `fist`/`open`/`pinch` presets, fan mode, position/torque control modes, torques and sensor calibration. These topics can actuate or reconfigure hardware. The published topics are `/joint_states`, `/hand/tactile/forces`, `/hand/tactile/pressure`, and `/hand/joint/raw`. Reported 50/50/20 Hz values are configured timer rates, not measured bus or hardware throughput.

Simulation dependencies are `pybullet`, `mujoco`, and (for the supplied MuJoCo example) `numpy`. Run examples from the directory containing the URDF/XML and mesh folders. The PyBullet script defaults to `D21_Right.urdf`; MuJoCo defaults to `D21_Left.xml`. The README's references to editing `xml_path` do not match the MuJoCo script, which embeds the filename directly in `MjModel.from_xml_path`. Both examples start GUI loops at import time; they were inspected but not imported or launched. Headless checks use separate short scripts, never the vendor GUI scripts.

## Known behavior and limitations

1. **ROS2 default startup commands motion.** `use_simulation` defaults to false; node initialization opens the interface and writes all 16 angle targets to zero (`hand_controller_node.py` lines 20..28, 91..126, 204..213). Use explicit simulation mode for offline work. Physical bring-up needs separate authorization and a clear operating area.
2. **Visualization is commanded position, not measured feedback.** The node builds `/joint_states` from `target_hw_angles`, including when writes fail (lines 269..299). Hardware readbacks go to `/hand/joint/raw` (lines 322..330). A moving RViz model is not proof of hand motion or command acceptance.
3. **Connection failures fall back to simulation.** Hardware initialization exceptions set `use_simulation=True` and the node continues (lines 114..122). Check logs and the actual mode; a running process is not hardware validation.
4. **Write acknowledgement validation gaps.** Both core variants check slave and CRC but do not require the expected normal function code or echoed address/value/count (`D21ModbusCore.py` lines 103..117). A synthetic valid-CRC response with function 0x03 is accepted by `_parse_write_response(..., 0x06)`. Five-byte Modbus write exceptions are rejected as incomplete before exception decoding. These defects were reproduced without hardware and left unchanged in vendor originals.
5. **RS485 exception framing.** The transport reads eight bytes for all writes and interprets byte 3 of a read reply as payload length; standard five-byte exception replies therefore are not handled as such (`d21_rs485.py` lines 46..62). This needs protocol-level repair and hardware regression tests before production use.
6. **Supplier specification discrepancies.** Standalone code uses thumb rotation range -35..35 degrees, while English protocol Table 3.17 lists -25..35 but gives the -35..35 conversion formula. Code reads velocities at input registers 16..31, agreeing with the English XLSX but not the protocol table's 0..15. Code maps tactile XY raw 128 to +12.8 N and 129 to -12.7 N, matching the protocol piecewise formula but not its summary -12.8..12.7 N range. Obtain supplier clarification rather than silently choosing one claim for hardware acceptance.
7. **Simulation fidelity remains unqualified.** Complete model files and successful parsing/loading do not establish correct inertias, friction, collision behavior, coupling under load, or match to the physical hand. The supplied scripts apply the 0.85 thumb and 0.8 other-finger coupling ratios; the XML/URDF alone should not be assumed to enforce those script couplings.
8. **No tested platform or firmware matrix.** No firmware image, controller firmware compatibility matrix, hardware test report or automated functional test suite was present in the SDK/simulation folders. ROS2 tests supplied in the archive are copyright/style checks, not robot behavior tests.
9. **CAN FD data-rate configuration gap with python-can 4.6.1.** The vendor passes `data_bitrate=2000000`, `fd=True`, and `brs=True` as SLCAN constructor keyword arguments. Inspection of installed python-can 4.6.1 shows its SLCAN backend selects the FD data bitrate through `timing=BitTimingFd(...)`; the supplier's data_bitrate keyword is ignored. A serial-factory mock reproduced configuration writes `C`, `S8`, empty, `O`, `O`, without the `Y2` command for 2 Mbps. This is a compatibility defect, not a tested physical CAN failure. The supplier also uses deprecated `ttyBaudrate` (replacement `tty_baudrate`; removal scheduled by python-can for 5.0.0). Pin reviewed dependencies and resolve timing configuration before CAN FD qualification; a successful import does not validate CAN FD operation.

## Validation completed

- ZIP path safety, file enumeration and `testzip()` CRC: passed.
- AST parse: passed for 18 Python sources (5 standalone SDK, 2 simulation, 11 ROS2 including setup/launch/style tests).
- Python 3.8 grammar parse: passed for the five standalone SDK sources; this is not a run on Python 3.8.
- XML parse and mesh-reference resolution: passed for four URDFs and two MuJoCo XMLs. URDF mesh-reference occurrences: 40 + 40 standalone, 40 ROS2 left, 20 ROS2 right. All referenced assets exist.
- System Python 3.12.3: imported `D21ModbusCore` and `d21_rs485` with bytecode disabled and no transport construction.
- Pure core checks: known Modbus CRC vector `01 03 00 00 00 0A -> 0xCDC5`; 16 joint endpoint mappings and invalid-upper-bound rejection; valid read response parsing and CRC-corruption rejection: passed.
- Pure write-response probes: confirmed the defects described above; these are recorded failures, not passing transport qualification.
- ROS2 `python3 setup.py build --build-base /tmp/artly-d21-review/ros2-build`: passed. This only builds/copies the Python package; it is not a ROS2/colcon build or launch test.

- Isolated environment: `/tmp/artly-d21-review/venv`, Python 3.12.3, pyserial 3.5, python-can 4.6.1, MuJoCo 3.16.0, PyBullet 3.2.7, NumPy 2.5.4. Installed using `python -m pip install --no-cache-dir pyserial 'python-can>=4.6.1' mujoco pybullet`; PyBullet built from its source distribution for CPython 3.12. No system packages were changed.
- Safe module import checks in that environment: all four standalone SDK modules and all four corresponding ROS2 driver modules imported successfully without constructing an RS485/CAN device. ROS2 node import itself was not attempted because `rclpy` is missing.
- Headless MuJoCo: both left/right XMLs loaded unchanged, each `nq=nv=njnt=nu=21`; 100 steps completed with finite positions/velocities and zero recorded MuJoCo warnings.
- Headless PyBullet: both left/right standalone URDFs loaded unchanged in `DIRECT` mode, each with 31 total joints; 100 steps completed with finite positions/velocities.
- Headless probes used the short independent script `/tmp/artly-d21-review/check_offline.py`, with machine-readable results in `/tmp/artly-d21-review/offline-results.json`. They exercised zero-control model stepping, not the GUI examples, script couplings, contact manipulation, stability across the operating envelope, or physical fidelity.
- Portable repository checker subsequently added as `tools/check_offline.py` and run against the copied repository assets with the same isolated environment: 15 check groups passed. `provenance/offline-validation.json` records exact dependencies/results and known vendor defects separately. The checker exits nonzero on unexpected check failures and performs no device connections. The SLCAN defect probe substitutes a mock serial factory before backend construction; no hardware port is opened.

No serial/CAN connection, controller binary, hardware example, calibration, firmware write, or physical actuation was performed.
